## Context

The [owner's design](../designs/2026-11-09-build-wand-structure-copy-design.md) requires a copy of the entire selected box: container contents, sign text, decorations and animals. The current clipboard stores block types and permutation states, omits kept blocks, and has no entity snapshot. This ADR proposes the replacement; this issue adds only a test-pack probe, its recorded results, and documentation. Shipped behavior and the current spec remain unchanged.

### Evidence from the type definitions

These statements come from the installed stable `@minecraft/server` **2.11.0**, `node_modules/@minecraft/server/index.d.ts`, not a game run:

- `world.structureManager` exposes `createFromWorld`, `place`, `get` and `delete`. `StructureCreateOptions` has `includeBlocks`, `includeEntities` and `saveMode`; `StructurePlaceOptions` has `includeBlocks` and `includeEntities`, but neither options interface offers an entity predicate.
- `createFromWorld` defaults to World storage, so Memory must be explicit. `StructureSaveMode.Memory` is available. `Structure.size` gives dimensions, with a single block having size 1 on each axis.
- `createFromWorld` documents unique identifiers with a namespace, and throws `InvalidArgumentError` for invalid identifiers, oversized bounds or bounds outside the world. It does not document an allowed-character grammar or a numeric size limit. There is no `getMaxStructureSize` in this version.
- `delete` returns whether removal occurred and invalidates the structure object. `get` returns undefined for a missing structure. `place` can queue placement into unloaded chunks and documents `InvalidStructureError` among its errors. The probe uses loaded lane chunks.
- `BlockSignComponent` exposes front/back text and `BlockInventoryComponent` exposes container items. There is no stable interface to populate or read item-frame contents or to create paintings. Item frames are block entities, not containers, and paintings are not summonable on Bedrock. No definition promises the payload and entity round trips below.

None of these findings contradicts the [owner's design](../designs/2026-11-09-build-wand-structure-copy-design.md). The design keeps the 32,768-block copy limit unless the engine maximum differs; the engine maximum is a per-axis bound that allows more than 32,768 blocks, so the volume cap stays and the axis bounds are added on top of it (Decision 2).

The scenario is exclusive because the maximum captures span the full world height (384 blocks in the Overworld) and must not capture entities from another scenario. Its largest footprint, 65 x 65, fits the 121 x 91 lane; its height stays inside `Dimension.heightRange`. The maximum captures only read blocks. The small fixture box is cleared in `finally`, structures are deleted, and spawned entities are removed even after assertion failures. No real fleet vehicle is summoned (`vehicles: 0`), because fleet spawn registration can evict existing vehicles.

## Decision

1. Use an engine structure in explicit Memory mode for the clipboard, with blocks and entities included. Capture the full box, including air and block entity contents. Use unique lowercase namespaced names under `yasu_build:` (0178), delete replaced clipboard/undo structures, and keep no disk persistence.
2. Keep the final copy/cut **volume limit at 32,768 blocks** (`BUILD_SPEC.maxCopyVolume`), inclusive. Also reject a box whose X or Z exceeds 64 or whose Y exceeds 384, the engine's per-axis structure maximum measured by the probe; volume alone does not bound a long thin box such as 512 x 1 x 64. Show the existing "too large" style message and leave state unchanged in both cases.
3. Paste writes every cell including air; remove the Skip air toggle and `flow.skipAir`. Paste may overwrite containers and other kept block types. Existing vehicle-space, camp-space and laid-block protection still applies to the whole destination box.
4. Choose capture with `includeEntities: true` followed by **synchronous removal of newly pasted excluded entities**, using the set of destination entity IDs recorded before place. Exclude SUV, camper, sports boat and bulldozer using `ENTITY_TYPE`, plus the fleet's auxiliary deck seats, seat fillers and stand-ins. Never remove players or original excluded entities. This retains arbitrary non-fleet entity payload without a separate serializer; `includeEntities: false` would require a second capture/serialization mechanism for every decoration and animal.
5. Before paste or snapshot undo, remove existing non-player, non-excluded entities in the target box. Cut captures first, then removes the same eligible source entities and clears **all** source cells to air, including containers and kept blocks. Preserve original excluded entities. Use default `dimension.runCommand("fill ... air")`, without `destroy`, which the probe showed leaves no item drops from populated containers; split boxes into calls of at most 32,768 blocks. The probe's fixture clear is below that cap; the 32,768-block cube tests capture, not fill's command limit.
6. Before paste or cut, capture one Memory undo snapshot of the affected box. Undo replaces the whole box's blocks and eligible entities, including container contents, rather than skipping conflicting cells. At most one snapshot entry survives per player; retain the existing cell-record history and ten-entry policy for other edits. This does not introduce rotation, flip, stack, redo, disk storage or shared clipboards.

## Consequences

No production module or shipped asset changes in this issue. Update the build-tools spec alongside the later implementation, preserving its current behavior descriptions until then. `build_structure_probe` stays as a permanent in-game test of these engine facts (0188), so an engine upgrade that changes them fails CI.

The exclusion probe establishes only the proposed mechanism on a stand-in. It cannot establish fleet-hook timing, real vehicle payload behavior, or protection against copied auxiliary entities registering before removal. Production implementation must establish that the synchronous filter runs before fleet admission/eviction, or arrange admission filtering in the vehicle integration before enabling structure copy. If this cannot be guaranteed, revisit the exclusion approach; deleting copies after registration is too late to protect fleet limits. The test pack's dynamic properties also cannot prove preservation of production-pack ownership metadata.

Frame inventory access and painting summon were found unsupported on Bedrock, so these checks moved to `build_structure_decor_probe` (`needsPlayer: true`). The store adapter's item-frame contents and painting checks live in `build_structure_store_decor` (`needsPlayer: true`), covering capture, clearEntities, clearBlocks, and place through `BedrockStructureStore`. Both scenarios run only when a player is logged in and are skipped in CI; all other checks in `build_structure_probe` remain headless. Setup is player-driven: when prompted, the player places the frame, inserts a diamond, and hangs a painting. The scenario observes frame contents by breaking the frame with `setblock ... destroy` and looking for the diamond drop, validating this observation on the original before the structure round trip. Item-frame contents and painting restoration in both scenarios remain unverified until run with a logged-in player; manual rows BT32 and BT33 record these checks. With a player connected to the dev BDS, run `GAME_TEST_FEATURES=build pnpm test:game`; both run with the other build scenarios. Accepting this ADR does not claim either is preserved. Custom banner patterns, head skins and painting artwork also require manual checks before claiming those payloads are preserved.

Whole-box undo can overwrite later edits, and copying containers intentionally duplicates items on this home LAN server. Memory snapshots consume more memory than cell records; one snapshot per player bounds history but not clipboard sizes across players. Revisit on engine upgrades, on failed cleanup, or if fleet exclusion cannot precede admission.
