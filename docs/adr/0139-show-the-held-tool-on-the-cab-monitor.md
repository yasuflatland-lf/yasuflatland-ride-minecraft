# 0139. Show the driver's held tool on the cab monitor

- Status: Proposed
- Date: 2026-10-24
- Extends: 0009, 0010, 0020, 0050, 0055, 0090, 0093, 0138

## Context

The owner wants the cab monitor to show the icon and state of the tool the driver holds. Every viewer sees the screen. The label is English pixel art with no localization. Only items in the kind's tool creative group count, because more tools will be added. Other vehicle kinds will follow later, so the core must stay kind-neutral. The bulldozer is the first kind: its Blade Up/Down switch shows UP or DOWN (0138).

The bulldozer's existing 32x1 palette texture has no room for pixel art. The stable Script API cannot read creative groups at runtime; the catalog is generated by `tools/gen_item_catalog.py` into `packs/yasu_ride_bp/item_catalog/crafting_item_catalog.json`.

The Behavior Pack pins `@minecraft/server` at 2.2.0, while `package.json` pins its typings at 2.10.0. The selected-slot inventory read already runs in `src/infrastructure/shared/dyes.ts`: `Player.selectedSlotIndex` and `getComponent("minecraft:inventory").container.getItem()`. `src/infrastructure/vehicle/bedrock/bedrockVehicleWorld.ts` already sends engine commands through `Entity.setProperty`. The feature uses only these APIs, not `EntityEquippableComponent`, `playerHotbarSelectedSlotChange`, `playerInventoryItemChange`, or `uv_anim`.

## Decision

1. **Opt-in profile.** A kind opts in with `VehicleProfile.monitor?: MonitorRule`. A rule lists the tools of one creative group, each as a `MonitorTool` with an ordered list of named states. Without a rule, the kind has no monitor (0050). Only the bulldozer gets a rule initially. Keep the shared monitor logic in a new core subfolder, `src/domain/vehicle/monitor/` (0090).
2. **Core property.** Reserve `monitor` (`yasu_ride:monitor`) in `CORE_PROPERTY_NAMES`, so no kind contract may use that name (0055). Its spec is `monitorPropertySpec(rule)`: int, range `[0, N]`, where N is `monitorScreens(rule).length`. In the pack it has default 0 and `client_sync: true`. Only kinds with a rule declare it.
3. **Screen order.** Value 0 is blank. Value `k + 1` is `monitorScreens(rule)[k]`, which lists tools in rule order and, within a tool, states in its `states` order. `monitorScreen` maps the held tool and its state name to this index. Holding nothing or an item outside the rule gives 0.
4. **Driver.** Only the Crew driver's held tool (`RiderView.heldTool`, from `seated.driver`) counts. With no driver, or while waiting for a driver, the screen is blank, except for the server-only test input below. Passengers never count.
5. **Tool state.** The state comes from the kind's optional `Drive.toolState?(item)`, which looks the item up in a per-drive `toolStates` table. The bulldozer blade shows its target (`bladeRaised()`), not its current height (0138), so a switch press changes the displayed state immediately.
6. **Tick and delivery.** Compute the value every drive tick and send it only on change through a `SyncedValue` (`src/domain/shared/syncedValue.ts`) on the `Vehicle`. Append its command to `stepCommands`. Include the value in `Vehicle.resync()` after a failed send (0127). Do not restore it: after `/reload`, the unprimed `SyncedValue` sends the current screen on the first tick.
7. **Held item read.** Infrastructure reads the selected-slot item only for kinds whose profile has a rule, using `profileOf(kind).monitor !== undefined`. Use the inventory read and `Player.selectedSlotIndex` already used under the 2.2.0 pin. Pass the item as a bare id when its namespace is `yasu_ride`, and undefined otherwise.
8. **Rendering (0009, 0020).** Generate a second geometry, `geometry.yasu_ride.<kind>_monitor`, and a second render controller, `controller.render.yasu_ride.<kind>.monitor` (0047), from the new data file `tools/monitor_screens.json` in `tools/gen_bulldozer.py`.
   - Use one atlas texture, `<kind>_monitor.png`, and one bone, `screen_<item>_<state>`, per screen.
   - Each bone's single cube is textured only on the face whose outward normal points at seat 0 (`down` for the bulldozer plate). In model space, before the model is turned 180 degrees, a positive x rotation tips +y toward -z in game; `tools/render_preview.py` draws x rotations with the opposite sign (0051).
   - Key `part_visibility` on the property.
   - Use `Material.lamp_lit` (`entity_emissive`). Glyph and icon texels have alpha 0 so they glow (0020); the background is opaque.
   - In the client entity, list the monitor controller before the controller that holds blended materials, and only when `query.property('yasu_ride:monitor') > 0`. Draw the opaque overlay first, then blend the glass over it.
   - Place the visible face at least 0.1 px in front of the screen plate it covers. Value 0 draws nothing, leaving the existing palette screen visible.
9. **Catalog consistency.** Keep the TS tool list equal to the creative group in `crafting_item_catalog.json` by a test, not runtime reads. This follows the data-mirror approach of `CAMPING_GEAR_IDS` (0093), whose bare ids are checked against `tools/camping_gear.json`. The monitor rule carries the group so the test can compare its tools with the catalog.
10. **Test hook.** Add the server-only script event `yasu_ride:test_held_tool`, with message `<vehicleId>,<bareItem>` or `<vehicleId>,clear`. It supplies the held tool only when there is no driver, as `testInput` does (0010).
11. **Adding a tool.** For a kind that already has a monitor, adding a tool requires only data and table entries, with no new branching. Implement the checks below with the feature so each missed step is caught.

| Step | Caught by |
|---|---|
| 1. Add the item to the kind's creative group in `tools/gen_item_catalog.py` | The group test in `tests/domain/vehicle/kinds/<kind>/monitor.test.ts` |
| 2. Add a `MonitorTool` entry to the kind's `MonitorRule` | The group test |
| 3. Add an entry to the drive's `toolStates` table | The kind-generic `toolState` test |
| 4. Add one row per state to `tools/monitor_screens.json`, with a label of at most 4 characters | The kind-generic pack test |
| 5. Map the item to its icon grid in the generator | A generator error |
| 6. Widen the `yasu_ride:monitor` range in `<kind>.se.json` to the new screen count | The kind-generic pack test |
| 7. Run `pnpm model` | `pnpm model:check` |
| 8. Bump the RP manifest version and the BP dependency on it (0015) | `scripts/check-rp-version.mjs` at release (the RP header version), and `tests/packs/resourcePack.test.ts` (the RP module version and the BP dependency match it) |

## Consequences

- One property covers any number of tools; adding a tool only widens the range.
- The idle look is unchanged: the blank screen draws nothing.
- `tools/render_preview.py` draws only the main vehicle geometry, so the previews do not change.
- UV orientation on the textured face needs an in-game check.
- The monitor generator code stays in `tools/gen_bulldozer.py` until a second kind needs it. Then move it to a shared module in a refactor PR of its own, before adding the variant (0050).
- The `.se.json` range is edited by hand and checked by a test.
